- [ ] 입력
    - [ ] 입력 값 검증
- [ ] 출력
    - [ ] 실행 결과 출력(1 반복에 1번씩 출력)

# 구현 목표

- 확장 가능한 구조 -> 다양한 디자인 패턴들을 생각하며 확장을 신경썼습니다. 나중에 기능을 추가할 때 이게 확장에 도움이 되는지 확인해보고 싶습니다. 
- 테스트 주도 개발 -> 정말 쉽지 않았고, `SimpleRacingRule` 부분은 만들고 나서 나중에 테스트 커버리지를 올렸습니다. 그래도 최대한 노력했습니다.
- 1기능 1커밋 -> 끝까지 정신 붙들고 지키려고 충분히 노력했습니다.
- 추상화를 이용한 느슨한 결합 -> 어느정도까지 해야 적당히 추상화를 한건지 고민을 많이 했습니다. 과하지 않으려 노력했습니다.

# 코드의 의도

1. 레이스의 현재 상황을 "실시간"으로 볼 수 있어야 된다고 생각했습니다. 
따라서 뷰 <-> 컨트롤러 <-> 서비스가 연결을 유지하며 레이스의 실시간 정보를 계속 전달 하도록 만들었습니다.
`RacingController.startRace()` 부분이 이에 해당합니다.

2. 요구조건의 변화를 생각하여 차의 전진 조건과 레이스에 등록 가능한 차량의 이름 길이, 이름 중복 허용, 길이 제한 등을
동적으로 수정할 수 있도록 만들었습니다. 각각 `Car`-`Condition`, `Race` - `Rule` 에 해당합니다.

# 개선이 필요하다 생각하는 부분

### 1. `RacingController` 에서 `Race` 객체를 알고 있는 것

`Race`를 식별할 수 있는 값만 가지고 `RacingService` 에게 요청하는 방법이 괜찮을 것 같습니다.

### 2. `Condition`, `RandomNumberCondition` 명명 및 패키지

`Condition` 은 `Car` 의 전진 조건을 유동적으로 설정할 수 있도록 설계된 인터페이스 입니다.
설계 당시에는 실제 차량과 비교했을 경우 엔진 같은 느낌이라고 생각하고 설계를 했습니다.
허나 `Engine` 이라는 이름은 요구사항과는 거리가 멀어지는 느낌이 들어 "조건 -> `Condition`" 으로 명명했습니다.
패키지는 어디에 어떻게 만들어야 할지 고민을 많이 했으나 우선 entity에 뒀습니다.

### 3. `CarFactory` 의 동적 `Condition` 설정 방식

`enum`을 어떻게 잘 이용해봤으면 더 좋았을 것 같습니다.

### 4. `Race`

`Race` 가 이번 과제의 핵심이라고 생각합니다. 
이 부분에서 기능을 얼마나 잘 분리하느냐가 중요했다고 생각하는데 그러지 못한 것 같습니다.
`Race` 에서 너무 많은 일을 담당하고 있다고 생각하고, 
우승자를 찾아내주는 `RaceAnalyst` 정도는 있었으면 기능 분리가 됐을까 생각합니다.

### 5. `Rule`, `SimpleRacingRule` 패키지

`Rule` 은 `Race` 에 적용 시킬 조건을 설정하는 인터페이스입니다.
`Race`의 경우는 `Rule` 을 저장하지만 `Rule` 의 경우 다른 `Race` 들도 쓸 수 있어야 된다고 생각하여 단방향 구조를 채택했습니다.
명명의 경우는 적합했다고 생각하지만 패키지는 적합하지 못한 것 같습니다.
그래도 개인적으로는 `SimpleRacingRule` 의 경우 잘 설계한 것 같습니다.

### 6. `RaceFactory` 추가

`Car`에게 `CarFactory` 가 있어서 동적으로 `Condition` 을 설정했던 것처럼 
`Race` 도 `RaceFactory` 가 있었으면 동적으로 `Rule` 설정이 가능했을테니 더 좋았을거라고 생각합니다.
일단 만들어두면 나중에는 IO부분에서 입력만 똑바로 받도록 수정만 하면 기능 추가가 쉬웠을 것이라고 생각합니다.

### 7. `io`

`io` 부분은 정말 지저분하게 코드를 만든 것 같습니다. 다음 과제에서는 이 부분에 있어서 충분히 역할을 나눠야 할 것 같습니다.
너무 고민을 많이한 결과 뭔가 짬뽕이 되면서 이도저도 못하게 된 것 같습니다.
